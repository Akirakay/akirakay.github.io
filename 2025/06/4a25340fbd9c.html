秒杀系统学习笔记

Posted at 2025-06-24 Java  Java Concurrent 秒杀 

核心问题

秒杀主要解决的是两个问题：并发读、并发写

从用户到应用的链路的过程中尽量遵循：请求的数据和数量尽量少、链路尽量短、依赖尽量少、尽量避免服务单点

在秒杀架构的设计上需要保证：

  • 稳-高可用
  • 准-数据一致性
  • 快-高性能

架构原则

秒杀系统本质上就是一个满足大并发、高性能和高可用的分布式系统

架构的思考要素

  1. 减少请求的数据
    请求的数据网络传输需要时间，并且数据的解压缩、编解码、序列化和反序列化等操作都是比较消耗CPU的操作，占用CPU资源
  2. 减少请求数量
    减少非必要请求数，可以有效降低请求过程中在DNS解析、三次握手等方面的时间消耗
  3. 路径尽量短
    从发出请求到返回数据的整个路径过程中，依赖的节点数越多，建立的连接数就会越多，从而导致请求的可用性降低
  4. 依赖尽量少
    对完成一次用户请求必须依赖的系统或者服务，视为强依赖。在保证业务核心服务的前提下，其他的依赖尽量少，避免非核心服务拖累核心服务
  5. 避免有单点服务
    服务的无状态化，解耦服务状态与机器，避免因为服务单点失败，导致整条业务处理链路宕机

追求性能的极致，意味着”定制化“越多，通用性就相对来说会降低

动静分离

  • 把静态数据缓存到离用户最近的地方：类似浏览器存储、就近CDN服务器、服务端Cache
  • 直接缓存 HTTP 连接：直接缓存 HTTP 连接而不是仅仅缓存数据

二八原则：热点数据

处理热点数据：

  1. 优化
  2. 限制
  3. 隔离
    临时缓存热点数据，将限制热点数据在一个请求队列，且热点数据单独隔离，避免对其他业务造成影响。

流量削峰

  1. 请求队列
  2. 添加中间操作，拉长请求时长，缓解单位时间请求数据量
  3. 分层过滤：在不同的层次尽可能地过滤掉无效请求，让“漏斗”最末端的才是有效请求

性能瓶颈

因素：CPU、磁盘IOPS、RT
发现瓶颈：JProfiler 和 Yourkit 工具查询是否QPS极限时，是否CPU usage > 95%
优化：

  • 减少序列化
  • 并发读优化

“减库存”核心逻辑

三种减库存的方式：

  1. 下单减库存
  2. 付款减库存
  3. 预扣库存：下单后库存保留时间，超时释放(比较多采用✅)
